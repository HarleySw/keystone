# Keystone Flow — Deep End-to-End Execution Flow Anatomy (`learn-from-code` Single-Pass Walkthrough)

Build codebase mental models and debugging intuition for any cohesive end-to-end workflow or feature pipeline without a `git diff` by prioritizing **completeness of core mechanics over arbitrary length caps (`Micro-Cap, Not Macro-Cap`)** and **3-second visual comprehension**: open with a standardized routing header and a 100% plain-language macro story, trace the main execution spine in 3–6 crisp steps, explain every guard and unfamiliar API contract with `< 76`-char subgoal-commented code and conversational vertical case walkthroughs (`✅`/`⚠️`/`❌`), and close with actionable `"Where to Touch"` recipes and reusable patterns in a single complete pass.

**Save standalone flow docs to:** `docs/keystone/flows/YYYY-MM-DD-<flow-slug>.md` *(Or `docs/keystone/map/flows/flow-XX-<name>.md` when invoked from `keystone:map`; user preferences for location override this default)*

## When to Use (Scale-Based Routing: `flow` vs. `map` vs. `decode`)

- **Use `keystone:flow` when (1 Cohesive End-to-End Flow Across Files):**
  - Tracing how a specific feature, business workflow, API endpoint, webhook, CI pipeline, background job, or CLI command executes end-to-end across files without a `git diff`.
  - Writing or updating a deep flow file (`docs/keystone/map/flows/flow-XX-<name>.md` or `docs/keystone/flows/YYYY-MM-DD-<flow-slug>.md`).
  - Asking *"How does flow X work and where do I touch code to modify or extend it?"*
- **Do NOT use `keystone:flow` when:**
  - Mapping an entire unfamiliar repository/monorepo, auditing 100% module coverage (`.keystone/map/01-coverage-ledger.md`), or generating repository-wide atlases and `AGENTS.md` contracts (**REQUIRED SUB-SKILL:** Use `keystone:map`).
  - Explaining a single isolated `< 30`-line function, bitwise expression, or regex line-by-line, or reviewing a `git diff` / commit patch with a 2-turn Quiz Gate (`decode`).
  - Debugging a specific runtime stacktrace, crash, panic, or deadlock (`trace`).

## Inline `using-keystone` / `learn-from-code` Language, Syntax & Visual Clarity Rules

Apply these exact language and visual formatting rules across 100% of your flow `.md` file and chat response:

1. **Everyday Spoken Developer Language & Natural Code-Switching:**
   - Write 100% of headers, bullets, walkthroughs, and inline `//` comments in the user's active language with **zero dual-language parenthetical headers** (never write `<Local Label> (<English Label>):`) and **zero academic jargon** (`RAD-AI E1`, `Zeller Infection Chain`, `QOC/ATAM`).
   - Preserve universal technical terms that native developers say daily in English (`git diff`, `commit`, `repo`, `monorepo`, `package`, `target`, `pipeline`, `CI/CD`, `script`, `shell`, `CLI`, `terminal`, `dict`, `list`, `array`, `object`, `struct`, `class`, `function`, `module`, `plugin`, `agent`, `wheel`, `binary`, `build`, `test`, `unit test`, `query`, `flag`, `config`, `race condition`, `deadlock`, `in-place`, `offset`, `stream`, `buffer`, `fallback`, `edge case`, `breakpoint`, `mock`, `payload`, `thread`, `async/await`, `callback`, `hook`, `state`, `migration`, `backfill`, `schema`, `atomic`, `middleware`, `dependency injection`, `router`, `idempotency`, `rdeps`)—never translate `wheel` as vehicle wheels, `shell` as outer shells, `agent` as textbook AI nouns, or `dict` as language dictionaries.
2. **Mechanical Plain-Language Syntax (`Concrete Actor + Strong Action Verb`, `One Word = One Meaning`, `Old-Before-New`):**
   - **Concrete Actor + Strong Action Verb (`Zero Zombie Nouns`):** Pair a concrete actor (`User`, `Router`, `CI script`, `Function X`) directly with a strong action verb (`overwrites`, `skips`, `blocks`, `prefixes`, `injects`, `validates`). Never open sentences with abstract nominalizations (*"The implementation of..."*, *"The execution of..."*).
   - **Ban "Translationese" & Literal Metaphor Calques:** Never translate English metaphors (`drop`, `isolate`, `deduplicate`, `preserve`, `hydrate`, `swallow`, `plumbing`) or internal document roles (*"coverage ledger"*, *"agent contract"*, *"data dictionary"*, *"control plane"*, *"execution spine"*) word-by-word into stiff phrases; use natural everyday spoken developer expressions. Never narrate low-level syntax operators pedantically (*"the ternary operator returns..."*).
   - **One Word = One Meaning & `Old-Before-New` Sentence Chaining:** Use the exact same term for a concept throughout the file (zero synonym rotation). Write short, complete sentences ending with a period (`.`) linked by `Old-Before-New` transitions (open sentence 2 with the concept or result produced at the end of sentence 1). **NEVER chain prose clauses with `->` arrows** and **NEVER write choppy telegraphic "half-prose, half-code" fragments** (`"✅ Branch 2a matches k === ..."`).
3. **Cross-Surface CLI & GUI Rendering Discipline (`< 76` Chars, Bite-Sized Bullets, Safe Links):**
   - **Bite-Sized Bullets (`Micro-Cap, Not Macro-Cap`):** Unlimited total bullets and code steps, but each individual bullet holds **1 single idea (`1–2` short spoken sentences)** using `**bold:**` for parent titles and `*italic:*` for child labels (never `***...***`).
   - **76-Character Width Cap:** Keep every line inside code blocks, inline `//` comments, ASCII diagrams, and ASCII rulers **strictly under 76 characters** (wrap long comments across consecutive `//` lines).
   - **Semantic Traffic-Light Icons Only (`✅`, `❌`, `⚠️`):** Ban decorative emojis (`🚀`, `💡`, `✨`, `📌`, `🔥`, `🔌`).
   - **Clickable Visible `filename:line` Links & Safe Backtick Escaping:** Format links as `` [`path/to/file.ext:line`](path/to/file.ext#Lline) `` on first mention in a section—never wrap `[label](url)` in outer backticks, never wrap backtick-containing expressions (`` `${a}_${b}` ``) inside single inline backticks, and never output raw HTML tags (`<br>`, `<details>`) or `mermaid` blocks.

## Single-Pass 5-Section Output Contract (`learn-from-code` Style)

Localize all section titles, bullet labels, explanations, and inline `//` code comments into the user's exact language using natural monolingual developer phrasing:

### 1. Big Picture (100% Plain-Language Macro Story)
Open directly with the 4 bullets below in natural spoken words. **Do not mention file paths (`pipeline.py:19`), function names (`get_package_step`), or local variable names (`reverse_deps_to_build`) in the 3 prose bullets**—save those for Sections 2 and 3. However, **ALWAYS name real tools, platforms, and everyday developer terms** (`Bazel`, `Buildkite`, `Git`, `CI pipeline`, `monorepo`, `package`, `wheel`, `commit`, `unit test`) directly instead of inventing riddle-like circumlocutions:
- **Goal:** State in 1–2 short, clear spoken sentences what capability or workflow this flow runs and when it triggers.
- **Key design challenge:** Open with a brief everyday analogy, then break down in bite-sized indented sub-bullets (each starting with a short `*italic:*` lead-in phrase, 1–2 short spoken sentences ending with `.`, zero `->` chains) why the obvious/naive approach fails in practice.
- **Core approach:** Summarize in 1–2 plain spoken sentences how this flow solves that challenge.
- **Concrete example (`Input -> Output`):** A noise-free `< 76`-char visual snippet (using `❌` and `✅` where helpful, starting with a `< 76`-char `// Anatomy:` comment only if unfamiliar low-level tokens appear) with vivid sample values illustrating what enters and exits the flow.

### 2. Main Execution Flow (3–6 Crisp Spine Steps — Max 1 Primary Mechanism Per Step)
- Trace the high-level path data takes from entry trigger to final output in **3–6 short, 1-sentence numbered steps** (starting each step with the real-world user or runtime trigger event) so the reader grasps the end-to-end spine in 15 seconds. Name **at most 1 primary function, script, hook, or config file per step** in backticks (with `` [`filename:line`](path#Lline) `` on first mention, never wrapped in outer backticks, and never disguised behind a vague noun phrase). Never write a 10-step wall of text narrating every tiny utility helper!
- **Core Data Model (Only When Non-Trivial Domain Schemas Exist):** If the flow mutates a database table, domain `struct`/`interface`, or shared payload schema, quote a compact `< 76`-char commented schema block right below the numbered spine. If the flow is a script or pipeline with simple arrays/dicts, **do NOT fabricate an artificial "State Lifecycle" section**.

### 3. Core Code Steps (Scaled to Actual Engineering Decisions — Micro / Code Level)
Divide into chronological steps matching the actual engineering decisions or guards (`#### Step 1: <Practical technical question?>`, `#### Step 2: ...`—filter out peripheral boilerplate, never omit a real logic step):
1. **Plain-language transition & Unfamiliar API / Mechanism Pre-Decoding (Before the code block):**
   - Connect this step to the previous one (`` [`filename:line`](path#Lline) ``) and state the **Business / Safety Rule** this step protects in plain everyday words (without reciting raw code syntax right before the snippet).
   - Immediately before the code block, list a bite-sized bullet for any unfamiliar library/CLI mechanism, query syntax, hook, or callback stating: **(a) what it controls**, **(b) when it runs**, **(c) what its incoming parameters hold**, and **(d) what its return value causes**.
2. **Complete step code snippet (`< 76` chars per line):**
   - Quote the complete code block for that step (keeping the **enclosing function/method/class signature** or script block, replacing only repetitive boilerplate with `...`), accompanied by `< 76`-char numbered **Subgoal Comments** (`// 1.`, `// 2a.`) in the user's language, concrete evaluated example values above branch/interpolation/fallback (`??`/`||`) expressions, a `< 76`-char `// Anatomy:` legend at the top if unfamiliar format/regex/DSL tokens appear, and an **ASCII Ruler Diagram** (`< 76` chars) with concrete numbers (`start 100 + len 30 = pos 130`) whenever non-trivial slice/offset/coordinate math occurs.
3. **Focused explanation below the code (2 items only, localized naturally with zero parenthetical English labels):**
   - **Why the code is written this way** (*Contrastive Why*): Bite-sized indented sub-bullets starting with `*italic (Step // 1. / Branch // 2a.):*` explaining in 1–2 short spoken sentences why each guard or condition is needed and what concrete bug happens if omitted.
   - **Step-by-step case walkthrough** (*Visual Dry-Run — Conversational Vertical Cards, Never Multi-Column Tables*): State shared initial context upfront, then format each scenario as an indented parent bullet (`- **Case 1 — <Plain-language scenario title>:**`) with 3 bite-sized child sub-bullets (`*Input:*`, `*How the code checks it:*`, `*Result:*` localized into the user's language) written in smooth, complete spoken sentences with `✅` and `❌` (or a `Vertical Interleaved Timeline t1..t4` for async/concurrency logic).

### 4. Verification & Hidden Risks
- **`⚠️ Defect Alert` *(When any bug, fragile query, silent failure, or scale trap exists in the flow or its callers)*:** Under a `**bold**` parent title (with `` [`filename:line`](path#Lline) ``), break the explanation into **3 non-redundant child sub-bullets** (never dump textbook terms like *"Zeller's 4-Link Infection Chain"*):
  - `*Scenario & symptom:*` The concrete setup with vivid sample values and the exact wrong behavior or crash the user/CI sees (1–2 short sentences).
  - `*Root cause:*` Explain the flaw in plain spoken words following `Old-Before-New` order without reciting raw syntax right before the code slice.
  - `*Buggy code & Fix:*` A compact `< 76`-char fenced code slice (`❌ Current` vs. `✅ Fix`) with concrete sample values in `//` comments.
- **Verified & Quick check:** State what works, an exact debugger `breakpoint` (`` [`filename:line`](path#Lline) ``) with the concrete **State Invariant expression** to inspect live, and the CLI command to test the flow.
- **Assumptions, Risks & Co-Change files:** Check persisted-data backward compatibility (`localStorage`/DB/cache), silent failures, `O(N^2)` scale traps, and coupled files that must be updated together (`**bold:**` parent title + `*Technical trigger & Coupled files:*` with `` [`filename:line`](path#Lline) `` and `*Impact & Mitigation:*` child sub-bullets).

### 5. Where to Touch & Reusable Techniques
- **Where to touch when modifying code ("To change X, edit Y"):** 2–3 practical extension recipes (`- **When adding/changing <task>:**`), each with 3 bite-sized sub-bullets: `*Where to edit:*` (`filename:line`), `*Companion files to update:*` (`filename:line`), and `*Safety rule to keep:*` (`✅`).
- **Reusable techniques for other projects:** Extract each worthwhile engineering pattern (`- **<English Pattern Name> — <Natural everyday phrase in user's language>:**`) using 4 bite-sized sub-bullets:
  - `*Core idea:*` 1–2 plain spoken sentences explaining the general problem and solution using familiar everyday examples.
  - `*Reusable code template:*` Self-contained, domain-independent `< 76`-char fenced code block with concrete sample comments.
  - `*When to use in other projects:*` Bite-sized sub-bullets describing concrete problem signatures where this pattern shines.
  - `*Tradeoff & when NOT to use:*` Bite-sized sub-bullets explaining boundary limitations and cleaner alternatives.
- **Closing 1-Line Colleague Offer:** End with 1 natural sentence asking if the user wants to fix the `⚠️` bugs found in Section 4 or explore another flow.
